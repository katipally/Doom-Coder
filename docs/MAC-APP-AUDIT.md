**Date:** 2026-06-07
**Scope:** Mac app target only (DoomCoder/ root + DoomCoder/AgentTracking/)

---

## 1. Architecture Summary

DoomCoder is a Swift 6.0, macOS 26-only, LSUIElement menu-bar app that combines a **Caffeine-style "keep Mac awake" engine** with a **CKSyncEngine-driven Agent Tracking layer** that watches six AI coding agents (Claude Code, Cursor, VS Code Copilot, Copilot CLI, Windsurf, Codex CLI) and mirrors their events to a paired iOS companion app. The UI is a custom NSPanel-based floating command surface (Raycast-style) plus a SwiftUI `NavigationSplitView` Configure window with four tabs (Agents / Connections / Logs / Settings), supported by a sidebar `NSStatusItem` and a Carbon `RegisterEventHotKey`-based global hotkey (⌥ Space, rebindable). A small `dc-hook` Swift helper is compiled in a shell-script build phase and placed in `Contents/Resources/dc-hook`; the host app copies it into `~/Library/Application Support/DoomCoder/dc-hook` and points every agent's hook config at that stable path. The app is **not sandboxed** (so it can spawn `pmset` and a unix-domain socket listener), and relies on a local SwiftPM package `DoomCoderCore` (the shared Mac/iOS data model) plus the upstream `Sparkle` SwiftPM for in-app updates. A separate `DoomCoderCompanion` iOS app consumes the published CloudKit zone.

## 4. Issues

### 4.1 Bugs

| # | Severity | Location | Issue |
|---|---|---|---|

## 5. Wins (preserve these)

1. **CKSyncEngine lessons baked into comments.** `CloudKitPusher.swift` opens with a 9-item list of "lessons baked in" — environment migration, singleton base tag persistence, re-entry guard, zone-before-engine, deferred engine flush, task-local marker workaround. These are all enforced in the code below. Future maintainers will thank you.
2. **App-Nap opt-out via `userInitiatedAllowingIdleSystemSleep`.** Clever choice: keeps the safety-net timer firing reliably without preventing system sleep. CloudKit still can't wake a sleeping Mac, but the `willTerminate`/`didResignActive`/`didWake` lifecycle hooks are wired to flush state.
3. **Token-based monotonic correlation in `ApprovalArbiter`.** The `ingestSeq` counter on `AgentTrackingManager` is incremented per ingest, and the arbiter only cancels a deferred alert when a *later* event arrives with the same sessionKey. This is correct and clock-skew-independent — exactly the right approach.
4. **Pre-decision vs reliable permission hook classification.** `TrackedAgent.permissionHookReliability` cleanly partitions the 6 agents into two reliability classes. The arbiter treats them differently. This is the single most important UX win in the app.
5. **SQLite in serialized mode with WAL + `nonisolated` writes.** `EventStore.swift` opens with `SQLITE_OPEN_FULLMUTEX | SQLITE_OPEN_CREATE`, enables WAL + `synchronous=NORMAL`, then uses a dedicated `DispatchQueue` for writes while MainActor reads. This is the textbook-correct way to share SQLite between a SwiftUI body and a background event ingest.
6. **JSONC-tolerant read for VS Code settings.** `AgentInstallerV2.stripJSONC` is a hand-rolled line/block-comment stripper that respects string literals. Idiomatic for `~/Library/Application Support/Code/User/settings.json`, which routinely contains `//` comments.
7. **Per-folder sentinel comment for codex_hooks feature flag.** The `// doomcoder-managed:codex-features v1 BEGIN/END` markers let uninstall strip the flag precisely. Same pattern would be a good fit for any future "managed block" in user config files.
8. **5s safety-net timer scheduled in `.common` mode.** `CloudKitPusher.start()`'s `Timer(timeInterval: 5, repeats: true)` is added to `RunLoop.main` with `forMode: .common`, not `scheduledTimer`. The comment explains exactly why (event-tracking run loop mode suspends `.default`). Same pattern is repeated in `CloudKitPusherLifecycle` (60s heartbeat, 1h reaper) and `AgentProcessMonitor` (30s CLI scan) and `AgentTrackingManager` (20s sweep).
9. **`HookConfigBackend` is a real Swift `actor`.** Read-modify-write of `~/.claude/settings.json` and friends is serialized by the actor. Comment explains why this matters (Claude and VS Code both read this file).
10. **Run-anywhere Carbon `RegisterEventHotKey`.** Skipping the AX-permission requirement for the global hotkey is the right UX trade-off. The `conflictDetected` flag exposes the failure mode.
11. **`@Observable` + `@Bindable` throughout.** Idiomatic Swift 6 / SwiftUI 4. No legacy `ObservableObject`/`@Published`. `WindowOpenerBridge` + `dcOpenWindow` notification is a clean way to call `openWindow(id:)` from non-View contexts.
12. **Two-stage `agentInstalledStateChanged` + `agentInstalledStateChanged` notifications.** Triggers `validateAllHooks()` on the 60s heartbeat, drives the sidebar's "Set up →" prompt, and the green checkmark seal. Simple and effective.
13. **Pre-decision auto-approve spam fix** (`ApprovalArbiter`) is genuinely universal — covers Copilot CLI, Cursor, Windsurf. The 0.8s default defer window is conservative enough that a real human-blocked prompt will still notify within 1s.
14. **`Hooks folder for all 6 agents in a single place.** Per-agent token (`dc-hook claude <event>`, `dc-hook vscode <event>`, etc.) is the v2 installer's signature move — the recursive stripper uses the token to identify our entries even when the agent's own config is co-owned (e.g., Claude + VSCode share `~/.claude/settings.json`).
15. **macOS 26 design vocabulary.** `.glassEffect(.regular, in: .rect(cornerRadius:))`, `.thinMaterial`, `ContentUnavailableView`, `ShareLink`, `NavigationSplitView`, `TimelineView(.periodic)`, `.symbolEffect(.replace)`, `Animation.snappy/.smooth/.bouncy`. The app consistently uses the new vocabulary rather than mixing old and new patterns.
16. **Stable macID via `IOPlatformUUID` with random fallback.** Cached in UserDefaults so zone names are stable across app reinstalls.
17. **Compaction-tolerant Codable for `AgentNotificationPrefs`.** Custom `init(from:)` that decodes-if-present for every key — lets the on-disk JSON grow without breaking users on older builds. The comment explicitly explains why the synthesized decoder wouldn't suffice.
18. **Privacy manifest is minimal and honest.** Only `UserDefaults` (CA92.1) and `FileTimestamp` (C617.1) are declared. No tracking, no collected data types. Slight gap for "Apple system" reasons if the app uses `NSWorkspace` heavily, but otherwise clean.
19. **`@preconcurrency import UserNotifications` in `ChannelTester`.** Pragmatic — `UNUserNotificationCenter` is not yet fully Sendable in the SDK, so suppressing the concurrency diagnostic is the right call.
20. **Per-agent token-bucket rate limiter with `NSLock` + `@unchecked Sendable`.** Tiny, correct, testable. The "one warning per depleted window" UX is a small but thoughtful detail.

## 6. Clarifying questions for the user

1. **Mac App Store distribution:** Is the app intended for Mac App Store distribution? `app-sandbox = false` is a hard blocker for MAS. If yes, what would the alternative hook-installation story be (entitlements, XPC service helper, etc.)?
2. **dc-hook architecture:** The current `PBXShellScriptBuildPhase` + `xcrun swiftc` is fine for the current single-arch build, but if you want universal binary (arm64 + x86_64) and hardened-runtime codesign with **fail-fast** (no `|| true`), the script needs to be replaced with a `PBXNativeTarget` for the helper that builds an `.xcframework` via `xcodebuild -create-xcframework`. Is that on the roadmap?
3. **Swift 6.2 vs 6.0 skew:** Should the target's `SWIFT_VERSION` be bumped to `6.2` to match `DoomCoderCore`'s `swift-tools-version: 6.2`?
4. **FoundationModels engine:** `FoundationModels.framework` is weak-linked, but the app uses `AppleFoundationEngine` (via `DoomCoderCore`). Is the Apple Intelligence engine available on the same macOS version the app requires, or does it need additional availability checks?
5. **DC hook's `proc_pidinfo` struct:** Is there appetite to replace the hand-laid `DCProcBSDShortInfo` with `proc_pidfdinfo(PROC_PIDFDT_SHORTBSDINFO)` (which uses a public, stable struct)? It would be more future-proof against kernel-header changes.
6. **Static `pendingTab` in `ConfigureAgentsViewV2`:** The `static var pendingTab: Tab?` pattern is used to route a cold-launch from `WindowOpener.openSettings()`. Is this reliable, or have you considered using `Window` scene `value`-based routing (e.g., `WindowGroup("settings", for: SettingsTab.self) { … }` with `openWindow(value:)`)?
7. **Master toggle write race:** The master toggle writes to `UserDefaults.standard.set(Date(), forKey: CloudKitPusherDelegate.masterChangedAtKey)` from `PanelRootView`, and `CloudKitPusherDelegate.applyControlCommands` reads from the same key for the "local change wins" comparison. Are you sure the date comparison is consistent across timezones and clock drift? Consider using `Date.now` (which is monotonic) or an `Int` counter instead.
8. **Sleep assertion `deinit`:** `SleepManager.deinit` is `@MainActor`-isolated, but it `IOPMAssertionRelease(assertionID)` and invalidates timers. For a long-lived singleton this is fine, but if the singleton were ever released (e.g., on logout in a future sandboxed world), would the `prepareForTermination()` already have run? Worth a precondition.
9. **CloudKit zone wipe on environment bump:** The `localResetGeneration = 2` constant in `setupSyncEngine()` is hard-coded. If a future release needs another wipe (e.g., another dev-environment reset, a schema change), it must be bumped. Is there a process for when to bump it?
10. **EventStore retention:** `EventStore.retentionDays` defaults to 7, configurable to 1/7/30 via the Logs footer. Is there a UI to set per-agent retention, or a "high-volume" mode that purges more aggressively (e.g., 1 hour) for a noisy agent?
